# 生成任务积累循环（grow loop）首轮

日期：2026-11-06。状态：已执行（1 次登记运行 + 1 次开发冒烟）；反例审查已完成，推翻了"库组优于从零组"的比较（§6）。
边界：MuJoCo 仿真；1 个保存初态上的空手到位保持任务；不涉及抓取、实体或 VLA。

## 1. 为什么改流程

此前每一轮积累都是一个一次性脚本（`calibration/` 下 60 余个，`t01_artifact_v6`–`v9` 各一个），
每轮只有 1 个初态、模型请求上限 2–4 次。`runs/local_artifact_cycle_20261106_004/` 的两个候选
都因动作字段名（`action.type` 与 `action.op`）在第一条关节命令前失败，耗尽了修订预算。
积累因此一直没真正开始。

本轮换成一个由配置驱动的循环，取代逐版本脚本：

```text
任务生成器（种子 → 采样值落盘，私有正例构型）
  → 正例对照（特权关节插值，逐任务）
  → FAST：库中候选代码原样执行，0 次模型调用
  → SLOW：提议模型写代码 → 干跑接口门（不耗物理回合）→ 物理回合
          → 独立回放评价器判分 → 批评器诊断 → 反馈给下一次提议
  → 成功代码按内容寻址入库（candidate），记录 parents 与逐任务证据
  → 冻结库，留出任务只走 FAST；同一批留出任务另跑从零提议对照
```

## 4. 这证明了什么、没证明什么

证明：
- 在这台 plant、这个出口和这个评价器下，循环能端到端跑通：生成 → 提议 → 接口门 → 物理 → 独立判分 → 入库 → 精确复用。
  一次成功的提议之后，同分布的新任务（含留出种子）不再需要模型调用。
- 干跑接口门把格式类错误挡在物理回合之外。上一轮正是这类错误耗尽了预算。

没证明：
- **前沿上的能力生长**：reach 这一层被一份通用 IK 代码覆盖，库没有增长，也没有组合。
  这一层只能当作循环本身的验证，不是"在能力前沿长出新能力"的证据。
- 跨初态、跨场景泛化：18 个任务共用同一个保存初态，只是目标不同。
- **库组优于从零组**：反例审查推翻了这一点（§6）。从零组的 5 次失败全部是 `NOT_HELD`，其中 4 次失败的唯一原因是记录器的采样缺口。
- 抓取、长程组合、VLA 工具分支：均未接入。
- 正式 Skill：库条目全部是 candidate，本轮不做晋升。

## 6. 反例审查

新 context 审查只读核对了全部 54 条轨迹，物理没有重跑。我独立复核了第一条发现。

**评价器保持窗口与记录器缺口（推翻 C5）**：54 条 `trajectory.npz` 都在 t=2.000→2.052 s 处有一个 0.052 s 的采样缺口，
负对照在 19.35 s 处还有一个。成因是 `grasp_optimization/pantry_robot.py:170` 用 `next_record += .05` 累加浮点数。
`harness/local_reach.py` 的 `hold_timing` 用 `max_gap_s=.051`，遇到这个缺口就重置保持窗口。
这个偏差只会误判失败，不会误判成功。如果去掉缺口规则，从零组的 5 次失败里有 4 次会通过：

- `heldout_scratch/reach_82101_000/scratch/attempt_02`：0.930 → 1.082 s
- `heldout_scratch/reach_82101_002/scratch/attempt_01`、`attempt_02`、`attempt_03`：0.898 / 0.698 / 0.858 → 1.050 / 1.400 / 1.560 s
- `heldout_scratch/reach_82101_005/scratch/attempt_01`：0.924 → 1.076 s

照此复算，从零组是 6/6。库组的唯一优势是它在 `hold_s + 0.65` s 之后才返回 `done`，正好越过这个缺口。
所以 §3 的 5/6 对 6/6 不能当作积累收益的证据。另外，"0 次调用"没有计入训练段的成本：2 次提议、1 次批评、2 个物理回合。

处理：`local_reach.py` 是既有登记评价器（缺口规则来自 `LOCAL_ARTIFACT_CYCLE_20261106.md` §5 的修复），本轮不改，
原判定全部保留；去掉缺口规则的数字只是事后敏感性复算。待决定的是，是否登记评价器 v3（例如把缺口阈值设为 0.06 s，
或修正记录器的累加方式），并对历史回合做双栏重算。

**其余核对**：
- C1（判分路径）减弱：只有缺口问题。没有目标泄漏；执行错误和保护触发都会判失败；正例对照没有计入 Agent。
  上臂和肘部接触评价器不检查，审查另行回放 54 条轨迹，没有发现这类接触。
- C2（输入合法）成立：Worker 只拿到公开契约、身体几何和本体观测；提示词里没有私有采样值。
- C3（精确复用）成立：17 次 FAST 的源码哈希都与库条目一致，提议调用为 0。
- C4（留出独立）成立：采样值已落盘，留出目标距训练目标 40–94 mm；但有两个开发种子的目标距留出目标只有 11–13 mm。
  开发种子的实际任务数没有记录，审查是按每个种子 12 个任务重新生成后比较的。
- C6（库不增长）减弱：SLOW 只在 FAST 失败时运行，所以只要 FAST 成功，库按构造就不会增长；这不是实证发现。
  任务也偏易：FAST 末 1 s 内位置误差 0.40–2.29 mm（容差 8 mm），姿态 ≤ 0.002 rad（容差 0.15）。
- C7（负对照）成立但偏弱：它只说明目标偏离了起点，而 3 cm 的最小行程规则本来就保证这一点。

**审查后修复**：`calibration/grow.py` 的接口门计数原为 `<=`，实际允许 5 次拦截而不是 4 次，已改为 `<`。
这次登记运行里没有任务触发这个上限，但运行时的依赖哈希登记的是修复前的版本。
库代码 `init` 里查找 `palm_site` 的分支是死代码，它用的默认值恰好等于真值，没有影响结果。
