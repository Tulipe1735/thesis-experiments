### 7.1 已有实验为什么还没有回答这个问题

`experiments/grow_up_harness_v2/PROTOCOL.md` §11.2 / §11.4 的旧 S 指声明式文字卡，旧 C
在实际 pilot 中只增加 `move_linear`；`calibration/t01_agent_pilot.py` 的 `action_schema()`
和 `prompt_for()` 可以核对。因此旧四组是“文字卡 / 插值工具”的开发比较，不能重命名为
“在线代码 / 可执行技能图”的消融。`calibration/t01_code_policy.py` 的 `prompt_for()` 始终
发送 `skill_card`，既非纯 code，也未在该入口提供受控的可执行技能图调用。

R_engineering / B2_wait 是评价器正负控制；固定程序的生成例迁移是工程参照。它们不替代
论文方法基线，也不证明组合机制的收益。此前围绕 T01 的字段、拒绝传播、IK、渲染和评价器
工作只作为实现准备与失败诊断记录，不再通过继续局部优化一组来代替正式比较。

### 7.2 主对照的操作定义草案

按用户提供的四项定义，技能应包含语义、可执行实现、前后置条件及评价准则。技能的底层实现
可以是代码；以下 code / skill 的区别是**执行时的组织与权限**，并非“有没有 Python 文件”。

| 条件 | 可在线生成的行为 | 可调用的长期技能库 | 需要限制的差异 |
|---|---|---|---|
| Code-only | 可写代码、单回合 helper、闭环控制和调试 | 不提供持久可调用的技能图 | 不因禁用技能而减少共同身体资料或基本观测；不能暗读技能源码或工程参考程序 |
| Skill-only | 可检索、选技能、绑定对象、参数化、排序与按反馈重规划 | 与组合组相同的冻结技能图及可执行实现 | 禁止在线改写技能实现或补入任意新动作代码；不削弱成只读说明卡或僵硬固定序列 |
| Code + Skill | 可用同样的代码能力，并组合或局部修复技能调用 | 与 Skill-only 同一快照 | 新代码受同一权限与保护；评测期只在回合内适应，不写长期库 |

可加原子动作规划组作下限，但它不是 pure code 的替代。既有 S0C0/S1C0/S0C1/S1C1 编号
继续保留历史含义；新实验使用另行登记的条件名，不追认旧结果。

“局部修复”在这个消融中先限定为同一回合内的补偿或组合代码，冻结库的实现本身不改。
若开放修改库实现，需要另列“允许库修订”因素。三组排名只回答组合系统是否有增量价值；
若主张超出相加的协同效应，则补齐“无库且无在线编程”的第四格（仍可结构化闭环调度
公共原语），并预先确定尺度，例如成功概率差上的 `p11 - p10 - p01 + p00`。

### 7.3 方法基线与内部消融分开

- **论文方法基线**回答与已有方法相比如何。优先查原论文、官方代码、必要权重和训练条件。
  原方法在其原 benchmark 的复现结果，与移植到 G1/MuJoCo 的适配结果分别报告；改变平台、
  控制器或 backbone 时明确标适配，不能直接搬原论文成功率与本地 T01 比较。
- **内部消融**回答 code 与 skill 的组合是否有额外收益。使用同一模型与公共运行时，且
  Skill-only 共享组合组的技能版本和质量；不拿无法接通的 VLA checkpoint 作唯一弱对手。
- 若已有论文已包含代码生成与技能复用，不能把“同时使用二者”直接当成创新；应具体指出
  我们新增的机制及其对应消融。文献核对前不定稿创新性结论。

### 7.4 能支持结论的最小公平条件

1. 同一已保存初态为任务配对块，各条件重置到相同状态。固定 LLM、公共感知、身体资料、
   共同动作出口、保护、评价器及预登记预算；原方法必须保留的差异单列，不能假装完全同条件。
2. 在查看测试结果前划分开发与新测试实例并冻结技能库。`control_2500`、280xxx–310xxx
   等已消费实例不能改称未见；通过物理资格和可见性检查不等于按策略成功筛选任务。
3. 运行顺序在任务块内随机或平衡，保存真实排程；模型重复嵌套在任务内。重复轨迹和同一
   初态的多个模型请求不当成独立任务样本。样本量、重复数和顺序种子尚未确定，不静默填入。
4. 所有组保留自身完整单回合上下文、反馈与预算内恢复机会。报告成功率、失败类别、token、
   模型/底层动作调用、仿真时间、墙钟与库构建成本，不只比较成功回合的速度。
   技能内部的观测、控制和重试全部计入；明确采用实际部署的延迟推进物理，还是统一的
   决策能力测试时钟。两种问题不同，不能把保留真实延迟后的差异全归因为推理质量。
5. 技能库对 Code-only 的额外知识优势与“结构化组合”的优势分开解释。若主张收益来自
   表达或调度机制，而不只是更多先验，应增加同内容文字/扁平程序库等信息匹配对照。
6. 若主张包含“成长”，另测相同初始库和练习预算下的库改进及冻结迁移；一次混合组胜出
   不能单独证明经验积累、自动技能形成或跨回合学习。库来源中的人工贡献分别报告。
7. 1 mm 官方评价器维持冻结；边界敏感性单列。VLM judge 当前只作诊断，不以其输出替换
   官方结果，也不为某组成功事后放宽门槛。

## 8. 以 artifact 积累和可组合覆盖为中心的诊断（2026-11-06）

日期：2026-11-06。状态：表示与执行入口已只读核对，积累机制为设计建议、未实现。
边界：MuJoCo 仿真；未运行新机器人回合，未修改正式晋升规则或已有产物。

用户进一步明确：同一个 artifact 映射出 code 和 skill 是一个方法切入点；技能图是另一个；
Grow Up 的重点是积累可复用的 artifact 库，用于跨尺度问题。本次以此为目标，不再沿用
旧记录中“跨尺度只属后续范围”的安排来搁置它。当前材料还不能证明这两项的新颖性或收益。

### 8.1 最强的具体发现：同源投影仍然丢失控制语义

`experiments/grow_up_harness_v2/artifacts/t01_cup_to_tray.yaml` 的首步 `orientation: keep`，
`harness/artifact.py::_emit` 将它保留到代码 `_move(..., 'keep')`，但 `_describe(WalkTo)`
只写目标和 yaw，不输出 orientation。当前生成的技能卡首步因而是
`walk to [-0.07, 0.34, 0.09] at yaw 0.0`。

本轮无物理推进的直接检查：只把该步 orientation 从 keep 改为 yaw，两个 `_describe`
结果逐字相同，而 `_emit` 结果不同。说明单一存储源并不自动保证投影保持调用方所需的语义。
这与历史 identity 四元数拒绝模式相容，但没有执行干预，不能把历史失败全归因于这项遗漏。
另有技能卡引用 `grasp` / `params` / `P` 等派生变量，调用方并不自动获得其完整定义。

统一 artifact 的收益应落在可检查的不变量：code、skill 说明、契约、依赖及评价规格引用
属于同一版本；说明投影不丢前置、顺序、姿态、失败出口等关键约束。哈希一致本身只防文件
漂移，不能证明说明语义完整。修复生成器与验证这项不变量应取代再次手调提示词；本轮尚未修。

### 8.2 不是正式规则要求整项成功，而是当前 T01 表示与闭环偏粗

原最小方案 §4 已写“局部到达与保持 → 抓持稳持 → 放置”，并明确不让放置阻挡前两项。
因此不能把阻力简单归咎于正式规则过严。但当前 YAML `IR` 硬性要求 plan/lift/correct/release
四个阶段及手指参数，实际围绕完整杯入盘程序构造，尚非通用局部能力的表示。

`calibration/t01_code_policy.py::run` 保存 answer/history、执行并调用整项 `tray_verify` 后结束，
没有将新代码提交、提炼为参数化候选、独立验证后进入下一轮库快照的步骤。
已有 `harness/experience.py::candidate_skill` 硬编码 TP01_CHAIN，`router.decide` 只认 TP01；
它们不等于 T01 artifact 积累路径已经接通。诊断限定于这些已查入口，不断言仓库完全没有
注册、验证或局部练习机制。

建议把候选的单元设为**一个有意义、可独立判定的局部效果**：例如空手进入可接近姿态、
在给定可接近条件下抓持稳持、在已持杯条件下完成承托释放。整项失败可以保留前段候选，
但不能凭 `EXECUTED`、打印的阶段名或视频推断该局部效果成功；需先定义局部判据、再独立
复算或运行见证。正式验证仍沿 paired / repair_lineage 路径，不借此放宽整项验收。

工程前缀或保存中间态可以支撑条件化的局部测试，但必须披露来源与适用条件；不可称完整
自主完成，也不能在最终组合中插入隐藏复位。跨尺度组合最终必须由真实前段输出接续下一段。

### 8.3 库规模应按有效覆盖与连接衡量

同一实现的多个 seed 是多条证据，不自动变成多个技能；版本、日志、失败总结也不与已验证
可调用能力混计。失败可以成为附证或候选经验，不能当作成功技能节点。

图至少区分两种关系：一个 artifact 调用/包含哪些子 artifact，以及一个执行效果能否支持
后续 artifact 的前置条件。前者形成多层复用，后者支持顺序组合；谓词文字匹配只是候选连接，
还需对象角色绑定、坐标系、姿态、抓持状态、作用域及真实交接证据。当前
`router.skill_graph` 的 pre/post key 包含关系不构成实际接续验证。

独立反例审查补充核对：`registry.skill_graph` 另有一套关系，只要源 post 与目标 pre
共享一个谓词名字便导出边；router 则要求完整 key 满足所有 pre。两者当前不能当作同义图。
`ir.validate_sequence` 只累加前段 post，没有撤销已失效条件，因而不能仅凭它推断长链持续
持杯等状态。实际 runtime 仍有逐步后置检查；本轮未证明这些静态差异造成了某次物理失败。

`calibration/t01_fast.py::bind` 目前仅接受已绑定保存初态的哈希，适合防止越界声称已验证，
但不能直接承担跨初态的积累与扩展。应区分“有证据的范围”和“待验证的目标范围”，后者只在
候选/练习通道探索，不把扩大声明范围当作已经扩大能力。

待设计的指标是：单位练习成本新增多少可验证局部效果、旧实现复用比例、真实接续成功、
新增任务覆盖、固定库快照在未见组合上的成功与成本。库文件总数仅是存量描述；覆盖不增加、
连接不成立的增长不能单独证明 Grow Up。

### 8.4 下一项应验证的循环，而非直接扩大库

先选 T01 中最早尚未可靠实现的局部效果，冻结其前后条件和合法接口。执行已有能力能到达
的前缀，只对第一个缺口提出新代码；候选在独立见证中通过后才可按已定规则进入相应库状态，
后续回合直接调用该版本，不要求模型重新实现整套清空、接近、抓持和放置。

这个循环的可推翻点是：新增候选是否真的通过局部判据；新的可接续范围是否增加；下一次
任务是否实际复用而不是重写；最终无隐藏复位的组合是否比原流程覆盖更多任务。分解本身
不保证抓持可达、投影保真或控制稳定，也不自动减少全部验证成本。

可达性也分开记录：有同接口工程执行见证、被明确约束排除、尚未知。有限 IK 尝试失败不等于
物理不可达，旧固定腰的 TP01 包络不外推到允许调腰的 T01。未知案例在原登记中保留，不在
测试后筛掉。TP01 已有局部 op 谓词和 runtime 检查，优先复用实际机制而不是另建同义模块。

如果要区分“分解”和“积累复用”各自的收益，最小比较可考虑：原完整流程、分解并独立验证
但不提供后续检索、同样分解且开放后续 artifact 复用。三者开发预算与反馈一致；检验共享
局部效果和不共享效果的新任务。该比较尚未登记或执行，不能先由设计断言闭环是主瓶颈。

对应的方法证据可分开收集：同源投影与分别维护视图的语义一致性；同一批 artifact 的图结构
与扁平库的复用/覆盖差异；同一初始库与资源下允许积累和冻结不积累的迁移曲线。三项分别
支持表示、组织和成长，不由一张 code/skill 三组排名替代。论文方法基线仍按 §7 保留。

本轮没有选择新阈值、seed 范围、样本数或重试次数，没有启动 `_007`，没有将工程结果晋升
为自主能力；也没有实现投影修复、通用 artifact 或 T01 局部评价器。上述优先级是针对用户
目标的设计判断，需用实际积累循环验证。

正例用同初态、同接口的工程执行见证应通过；没有可复现正例则先诊断，不能靠放宽判据
进入正式练习。参考程序和私有验收证据对候选作者隔离。控制通过后，只让 Agent 补第一个
缺口，保留代码、输入、返回、动作、所有失败和成本；先进入 candidate，正式资格仍遵守
既定验证路径。复位准备态的测试标为条件化，完整任务另判。

完成判据：控制有独立结果，候选有可定位的效果判定及资格记录；若失败，可精确区分生成/
接口/感知/控制/契约问题。一个 `EXECUTED` 或局部成功不能代替完整 T01 成功。

**步骤 4：实际复用与真实接续。**
冻结通过验证的实现、输入契约和库快照。后续登记的任务调用相同 artifact ID/version/digest，
记录检索、对象绑定、调用及结果，禁止用重新生成一份相似代码冒充复用。有 A→B 组合时，
从 A 的实际终态直接运行 B；即使 B 单独在工程准备态能成功，也不能插入隐藏复位。
声明边和有执行见证的边分别记录。只通过局部验证的能力仍只报告其局部适用范围。

完成判据：至少能明确回答“实际调用了哪一版旧能力、进入条件是否成立、是否少写/少试了
这一段、是否增加真实可接续范围”。失败照常交付；不因库条目增加就宣称 Grow Up 成立。

### 9.4 之后怎样做比较

首个循环完成后才扩展规模。局部诊断可用三种流程：A 原完整流程；B 分解并独立验证但
不给后续检索；C 与 B 同样分解，开放冻结 artifact 检索复用。用相同模型、共同观测/控制、
实际初态及预登记资源，训练任务可按缺口选择，评测实例提前冻结且不回流挑版本。
A→B 检验分解，B→C 检验复用；重复调用不充作独立任务样本。

正式贡献的对照仍分开：统一/分别维护视图检验语义一致性；同库 graph/flat 检验组织收益；
允许积累/冻结不积累检验成长；在线 code、固定 skill、组合三组和论文方法参照见 §7。
这些是分阶段设计，不要求下一 session 一次跑齐。不能以当前工程脚本或域外裸 VLA 充当
强论文方法基线。Harness VLA 有 RPent；COAP 共享库且离线改进，完整源码入口待核实；
Skill2Real 已结合代码与技能，因此仅有“code + skill”名称不证明新颖性。
